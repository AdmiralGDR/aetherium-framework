# Внутриигровая проверка и анализ модов

`aetherium-verify` — рантайм-компаньон Щита: позволяет игроку (или админу) **проверять и анализировать
загруженные моды прямо в игре** — какие моды есть, кто их подписал и совпадает ли их байткод с тем, что было
собрано.

## На что отвечает

Для каждого загруженного `AetheriumMod` `ModInspector.snapshot(ClassLoader)` строит `ModReport`:

| Поле | Значение |
|---|---|
| `modId` | идентификатор мода |
| `author` | автор из **водяного знака** Щита (`""`, если не подписан) |
| `verdict` | `SIGNED_INTACT` / `TAMPERED` / `UNSIGNED` |
| `classesChecked` | сколько классов атрибутировано моду (точка входа + объявленный контент) |
| `tamperedClasses` | классы, чьи байты не совпадают с манифестом целостности |
| `contentCount` | декларативные `@AetheriumBlock`/`@AetheriumItem` |
| `nativeGuard` | активен ли нативный (Zig) гард как бэкенд контрольной суммы |

Вердикт даёт `ModVerifier` (в `aetherium-shield`): сливает все `META-INF/aetherium/shield-integrity.txt` на
classpath и пере-хеширует байты каждого класса (SHA-256). Несовпадение = класс **правили после защиты** —
взломанный jar, внедрённый бэкдор или обойдённая проверка.

## Как использовать в игре

Загрузчик регистрирует встроенную команду:

```
/aetherium mods       # список модов с вердиктом, автором, числом классов и контента (в чат)
/aetherium verify     # сводка целостности; называет TAMPERED-моды (уровень 2)
/aetherium inspect    # (клиент) открывает прокручиваемый экран-инспектор
```

`/aetherium inspect` открывает `AetheriumModInspectorScreen` — прокручиваемый список с точными метриками
шрифта, отрисованный через настоящий UI-адаптер загрузчика (см. [ui](ui.md)); подделанные моды — красным.
Так как экран — чистый `AetheriumScreen`, весь инспектор раскладывается и hit-тестится **без игры** в
`ModVerifySelfTest` (`aetherium verify`).

## Принуждение (сильное по умолчанию)

Загрузчик запускает `ModVerifier` при инициализации и по умолчанию **отказывается инициализировать
подделанный мод**:

```
Aetherium REFUSES tampered mod 'x' — its bytes do not match the Shield integrity manifest.
```

`-Daetherium.shield.enforce=false` — режим только-отчёт (инспектор всё равно подсветит красным, мод
загрузится). Неподписанные моды (без манифеста) не затрагиваются. Отладчик/агент показывается отдельно
нативным гардом (см. [shield](shield.md)) — эвристика, поэтому сообщается, а не жёстко принуждается.

## Почему это суверенно

Верификатор зависит только от самого фреймворка: манифест целостности Щита, чистый UI-модуль и
без-зависимостный нативный гард Zig для быстрой нативной контрольной суммы (с откатом на чистый Java). Ни
внешней библиотеки, ни сервиса — фреймворк проверяет свои моды, в своём рантайме, на экране. `aetherium
verify` — офлайн-доказательство, `aetherium guard` — статус нативного гарда.

## Доказательство, что игра запускается (Фаза 25)

Главным приоритетом было, чтобы **разработчики фреймворка и авторы модов могли точно проверить, что
игра действительно запускается.** Теперь это покрывают две проверки — одна мгновенная и офлайн, другая
окончательная.

### Офлайн-барьер — `./gradlew verifyJar` / `check` (~1 с, без игры)

`ArtifactVerifier` получил проверку **межартефактного конфликта модулей** (`AE-MODULE-CLASH`), которая
воспроизводит краш запуска Фазы 25 без игры. Он перечисляет каждый модуль, порождаемый поставляемым
набором, — свободные классы каждого jar как один модуль, **плюс по одному модулю на `META-INF/jarjar/*.jar`**
(по имени файла, чтобы не сосчитать дедуп самого JiJ) — и падает, если какой-либо пакет встречается в двух
модулях. Старые «жирные» трансформер + загрузчик это **не проходят**, называя `org/aetherium/core …`;
релоцированная сборка **проходит**. `BootHarness` (`bootSmoke`) выполняет ту же проверку на поставляемом
наборе, а `ArtifactVerifierTest` фиксирует оба направления. Все три встроены в `check`, поэтому дефект графа
модулей валит CI, а не запуск игрока.

### Окончательное доказательство — `./scripts/launch-check.sh` (реальный headless-сервер)

Для абсолютной истины `scripts/launch-check.sh` загружает **реальный** выделенный сервер NeoForge 1.21.1
(headless — краш происходит при разрешении модулей, до любого окна, поэтому ни дисплей, ни аккаунт
Minecraft не нужны) с установленным фреймворком и проверяет: нет `ResolutionException`, фреймворк появляется в
списке модов FML, сервер достигает `Done`. Передайте дополнительные jar модов, чтобы установить и их. Это тот
же процесс, которым автор доказывает, что его собственный мод запускается на фреймворке, — см.
[how-to: доказать запуск](../how-to/verify-the-launch.md).

## Доказательство, что клиент рисует (Фаза 27)

Выделенный сервер доказывает, что игра *грузится*, но не что она *рисует* — а был клиентским багом
GUI (все экраны замылены). Теперь клиент покрывают две проверки:

- **Офлайн `AE-UI-BLUR`** (в `verifyJar`/`bootSmoke`, то есть в `check`): ASM по поставляемому jar утверждает,
  что `AetheriumScreenAdapter.render` не зовёт `Screen.render` (чей `renderBackground` повторно размыл бы готовый
  GUI). Надёжно, без игры — ловит регресс до того, как его увидит игрок.
- **Окончательно: `scripts/launch-check-client.sh`** загружает **реальный клиент NeoForge 1.21.1** headless под
  Xvfb с программным GL (llvmpipe) и проверяет: нет `ResolutionException`, фреймворк конструируется, клиент
  достигает маркеров титульного экрана / инициализации GL (`Backend library: LWJGL`, `Reloading ResourceManager`,
  …) — то есть GUI может рисоваться. **Аккаунт Minecraft не нужен** (офлайн-клиент доходит до титульного экрана и
  грузит моды без входа). Вместе с серверным `launch-check.sh` это доказывает запуск игры и для фреймворка, *и*
  для модов, с обеих сторон. Если окружение не поднимает программный GL, скрипт об этом сообщает, а офлайн-проверка
  + серверный запуск остаются истиной CI.
