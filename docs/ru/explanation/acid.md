# Движок ACID — надёжность уровня СУБД для взаимодействий модов

*Русский. English version: [`../en/acid.md`](../../en/explanation/acid.md).*

Фаза 19 применяет гарантии **ACID** из мира баз данных — атомарность (Atomicity), согласованность
(Consistency), изоляцию (Isolation), долговечность (Durability) — к инъекции байт-кода и off-heap памяти,
чтобы искоренить три классические болезни моддинга: **Heisenbug-и**, **тихую порчу состояния** и
**частично загруженные моды**. Каждый столп — чистый, тестируемый офлайн модуль со своим самотестом в
CLI `aetherium`.

| Столп | Гарантия | Модуль | CLI |
|-------|----------|--------|-----|
| **A** — атомарность | Хуки мода применяются «всё или ничего» | `aetherium-injector` (`txn`) | `aetherium acid` |
| **C** — согласованность | Возвращаемые значения хуков проверяются контрактом до запуска | `aetherium-cli` (`contract`) | `aetherium contracts`, `analyze` |
| **I** — изоляция | Мод не может тронуть FFM-память другого мода | `aetherium-security` | `aetherium domains` |
| **D** — долговечность | Каждый тик журналируется; перемотка при крахе | `aetherium-hotswap` (`ttd`) | `aetherium ttd` |

## Атомарность — транзакционные хуки

Базовый инжектор уже откатывает **один** класс к ванильному, когда его инъекция не проходит песочницу
верификации. Этого мало: если мод внедряется в классы A, B и C и падает лишь правка C, игра всё равно
запустится с переписанными A и B — **частично применённый мод**, источник Heisenbug-ов «работает-у-меня».

`TransactionalInjector` рассматривает весь набор хуков мода как одну ACID-транзакцию:

```java
TransactionalInjector engine = TransactionalInjector.create(verifyLoader)
    .mod("gravity_plus", gravityInjector, List.of(
        new TargetClass("net.minecraft...Entity",       entityBytes),
        new TargetClass("net.minecraft...LivingEntity", livingBytes),
        new TargetClass("net.minecraft...Player",        playerBytes)))  // не проходит верификацию
    .mod("speed_mod",    speedInjector,   new TargetClass("net.minecraft...Mob", mobBytes));

EngineReport report = engine.apply();
```

- Все целевые классы прошли → **COMMIT**: публикуются все преобразованные байты и ставится таблица хуков.
- **Любой** класс упал → **ROLLBACK**: *каждая* уже верифицированная правка мода отбрасывается, ничего
  не ставится, мод отключается. Игра сохраняет ванильные байты для всех классов, которых касался мод.

Откат **мягкий** (правило): падающий мод локализуется и отключается, тогда как транзакция каждого другого
мода идёт независимо. JVM никогда не падает — сломанный мод просто не загружается.
`EngineReport.published(binaryName)` отдаёт эффективную таблицу классов после транзакции, которая по
построению никогда не содержит частично применённый мод.

`aetherium acid` доказывает это end-to-end: мод с тремя хуками, чей **третий** падает, откатывает хуки 1
и 2 (проверено: ничего не опубликовано, классы работают ванильно), а здоровый соседний мод всё равно
коммитится и запускается.

## Согласованность — проверка контрактов

Аннотируйте логику хука через `@Requires` (предусловие на аргумент) и `@Ensures` (постусловие на
возвращаемое значение), используя маленький, пригодный для анализа словарь `Constraint`
(`NON_NEGATIVE`, `POSITIVE`, `NON_POSITIVE`, `NEGATIVE`):

```java
@Ensures(Constraint.NON_NEGATIVE)             // уровень освещённости не может быть отрицательным
public static int lightLevel(HookContext ctx) { ... }
```

`ContractAnalyzer` в CLI читает эти аннотации прямо из скомпилированного байт-кода и запускает
**базовый символический (знаковый) интерпретатор** по каждому методу: константы несут точный знак, `neg`
и целочисленные `+ - *` комбинируют знаки, а всё непрослеживаемое (переменная, результат вызова, поток
управления) становится `UNKNOWN`. Вердикт для хука:

- **SATISFIED** — каждый возврат доказуемо соблюдает ограничение.
- **VIOLATED** — возврат доказуемо нарушает его (предупреждение ещё *до* запуска игры, напр.
  `NON_NEGATIVE`-хук, способный `return -1`).
- **UNVERIFIED** — знак не удалось доказать (сообщается, но это не ложная тревога).

`aetherium contracts` запускает самотест; `aetherium analyze <jar>` теперь дополнительно сканирует каждый
класс на контракты хуков и печатает вердикты. Ничего не исполняется — это чистый статический анализ.

## Изоляция — домены FFM-памяти

`GuardedSegment` не даёт моду выйти *за пределы* выданного сегмента, но никак не мешает моду дотянуться до
сегмента *другого* мода. `MemoryDomainRegistry` закрывает пробел:

```java
MemoryDomainRegistry registry = MemoryDomainRegistry.create(SecurityPolicy.global());
MemoryDomainHandle domain = registry.allocate("mod_a", 64);        // нужна NATIVE_MEMORY
registry.open("mod_a", domain.domainId()).setInt(0, 0xA5A5);       // владелец: OK

registry.open("mod_b", domain.domainId());                          // SecurityViolationException!
registry.grantAccess("mod_a", domain.domainId(), "mod_b");          // владелец делится явно
registry.open("mod_b", domain.domainId()).getInt(0);                // теперь OK
```

Каждый домен несёт случайную `UUID`-возможность (`MemoryDomainHandle`) — 122-битное значение, которое
нельзя угадать или подделать. Мод может открыть домен **только** если он владелец или ему **явно выдан**
доступ владельцем; любой другой запрос — локализованное `SecurityViolationException`, а не тихая порча
состояния соседа. Выдавать и отзывать может только владелец, а выделение по-прежнему требует базовой
возможности `Capability.NATIVE_MEMORY`. `aetherium domains` доказывает весь жизненный цикл.

## Долговечность — Time-Travel Debugger

`StructArenaJournal` записывает **строго ограниченный** кольцевой буфер поменных *дельт* памяти над
`StructArena`. На каждом коммите он сравнивает живую арену с единственной теневой копией, объединяет
изменённые байты в пробеги и хранит только их before/after-образы как один кадр. Кадры живут в кольце
фиксированной ёмкости, поэтому объём ограничен `shadow + capacity × 2 × byteSize` независимо от числа
тиков (правило) — типичный тик, сдвигающий пару сущностей, стоит десятки байт, а не полный снимок.

`TtdEngine` ведёт симуляцию через журналируемые тики и замораживает сцену краха при сбое:

```java
TtdEngine engine = new TtdEngine(arena, /* ёмкость кольца */ 64);

engine.tick((a, tick) -> { /* физика: x += vx … */ });            // COMMITTED (дельта в журнале)
engine.tick((a, tick) -> { throw new IllegalStateException(); });  // FAULTED (не закоммичено, локализовано)

if (engine.hasFault()) {
    ArenaSnapshot crash  = engine.fault().faultState();  // арена в момент броска
    ArenaSnapshot before = engine.rewind(0);             // последнее «хорошее» закоммиченное состояние
    ArenaSnapshot older  = engine.rewind(5);             // на пять тиков раньше — байт-в-байт
    double x = older.getDouble(entityIndex, xField);     // инспекция любого прошлого значения
}
```

Падающий тик **не** коммитится, поэтому журналированная история цела — разработчик шагает назад по
последним «хорошим» состояниям тиков, чтобы увидеть, значение какой сущности испортилось перед
исключением. `aetherium ttd` прогоняет 2 000 тиков, доказывает, что объём остался под крошечным
постоянным потолком, реконструирует прошлые состояния байт-в-байт (с упором в границу окна) и ловит
локализованный сбой тика, сохраняя целостность истории.

## Гарантии

- **Никаких импортов Minecraft** в чистых модулях; транзакционный инжектор, домены памяти, словарь
  контрактов и журнал — все загрузчик-независимы и тестируемы офлайн.
- **JVM никогда не падает.** Любой путь отказа (плохой хук, межмодовый доступ, нарушение контракта,
  сбойный тик) становится локализованной структурированной ошибкой — доступность по построению.
- Ограниченная память: потолок кольца TTD не зависит от числа тиков
  (`StructArenaJournal.maxRetainedBytes()`).
